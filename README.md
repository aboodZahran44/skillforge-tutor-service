# SkillForge Tutor Service

**A standalone FastAPI microservice providing a retrieval-augmented (RAG) AI tutor for the [SkillForge](https://github.com/aboodZahran44/skillforge-lms) learning platform.**

This service was extracted from the SkillForge Django monolith via a genuine strangler-pattern migration: the tutor logic was built and proven working inside the monolith first, then moved here — with its own database, its own deployment lifecycle, and an explicit, authenticated trust boundary with the system that owns it.

## Why This Is a Separate Service

- **Different load profile.** LLM calls take seconds; the rest of the platform responds in milliseconds. Keeping the tutor on its own ASGI-based service (FastAPI/Uvicorn) means a handful of concurrent, long-running tutor conversations can never block unrelated requests elsewhere in the system — a real risk under Django's default synchronous request handling.
- **Independent deployment.** This service can be redeployed, scaled, or have its model/prompt changed without touching the monolith at all.
- **A real trust boundary, not a shared database.** This service owns its own PostgreSQL instance. It has no access to the monolith's user, billing, or enrollment tables — it only knows what a signed token tells it.

Full platform context, business overview, and system architecture live in the [main repository](https://github.com/aboodZahran44/skillforge-lms).

## How Authentication Works

Two distinct trust relationships, handled two different ways:

1. **End user → this service.** The Django monolith is the only system that knows who's enrolled in what. When a learner opens the tutor, Django issues a short-lived (5-minute), course-scoped JWT — `{user_id, course_id, enrollment_id}` — signed with a secret shared between the two services. This service verifies the signature and, critically, checks that the `course_id` in the token matches the course being requested. A valid token issued for one course is rejected on any other course's endpoint.
2. **Monolith → this service (service-to-service).** When a course is published, Django needs to push its content here for indexing. This isn't a user action, so it doesn't use JWTs — it uses a long-lived shared internal API key sent as a custom header.

## Tech Stack

| Component | Technology |
|---|---|
| Framework | FastAPI (ASGI, via Uvicorn) |
| ORM / migrations | SQLAlchemy + Alembic |
| Database | PostgreSQL 16 with the `pgvector` extension |
| Embeddings & chat | OpenAI API (`text-embedding-3-small`, `gpt-4o-mini`) |
| Auth | JWT (`python-jose`) for end users, shared API key for service-to-service calls |
| Streaming | Server-Sent Events (SSE) |
| Containerization | Docker, Docker Compose |

## API

| Method | Endpoint | Auth | Description |
|---|---|---|---|
| `GET` | `/healthz` | none | Deep health check — verifies live database connectivity, not just process liveness |
| `POST` | `/internal/lessons/ingest` | Internal API key (`X-Internal-Key` header) | Chunks lesson content and stores OpenAI embeddings |
| `POST` | `/courses/{course_id}/chat` | JWT (`Authorization: Bearer`) | Retrieves relevant course content and streams a grounded answer via SSE |
| `GET` | `/courses/{course_id}/ping` | JWT (`Authorization: Bearer`) | Minimal diagnostic endpoint for verifying token scope without triggering an LLM call |

Interactive API documentation (Swagger UI) is auto-generated by FastAPI and available at `/docs` once the service is running.

### Chat response format

`POST /courses/{course_id}/chat` returns `Content-Type: text/event-stream`. Each event is formatted as `data: <text chunk>\n\n`, terminated by `data: [DONE]\n\n`. Because this endpoint is `POST` with a bearer token, it **cannot** be consumed with the browser's native `EventSource` API (GET-only, no custom headers) — clients should use `fetch()` with a manual stream reader instead.

## Getting Started

### Prerequisites

- Docker and Docker Compose
- Python 3.13
- An OpenAI API key
- A running instance of the [main SkillForge monolith](https://github.com/aboodZahran44/skillforge-lms) if you want to exercise the full authenticated flow (issuing real tokens, syncing real course content). The service can still be started and health-checked entirely on its own.

### Environment variables

Copy `.env.example` to `.env`:

```
DATABASE_URL=postgresql://postgres:postgres@tutor-db:5432/tutor_service
JWT_SECRET_KEY=<must match the monolith's JWT_SECRET_KEY exactly>
INTERNAL_API_KEY=<must match the monolith's INTERNAL_API_KEY exactly>
OPENAI_API_KEY=sk-...
```

### Run it

```bash
docker compose up -d --build

# enable the pgvector extension (first run only)
docker compose exec tutor-db psql -U postgres -d tutor_service \
  -c "CREATE EXTENSION IF NOT EXISTS vector;"

# apply migrations
alembic upgrade head
```

The service is now available at `http://localhost:8001`. Check `http://localhost:8001/healthz` to confirm it started correctly, and `http://localhost:8001/docs` for interactive API docs.

### Verifying it end-to-end

With the monolith also running, issue a real token from a Django shell:

```python
from django.contrib.auth import get_user_model
from learning.models import Enrollment
from tutor.services import issue_tutor_token

user = get_user_model().objects.get(email="<some enrolled user>")
enrollment = Enrollment.objects.get(user=user, course_id=1)
print(issue_tutor_token(enrollment))
```

Then call the chat endpoint with that token as a bearer token against `http://localhost:8001/courses/1/chat`. Using the same token against a *different* `course_id` should return `403`.

## Ports

| Service | Port |
|---|---|
| FastAPI app | `8001` |
| PostgreSQL (pgvector) | `5433` (mapped to avoid colliding with the monolith's own PostgreSQL on `5432`) |

## Known Limitations

- No automated test suite yet in this repository — the JWT trust boundary, CORS configuration, ingestion pipeline, and SSE streaming were verified through live, manual end-to-end testing against a running instance (including deliberately mismatched tokens, real network requests from a browser, and a stopped-dependency health-check test), but none of that is currently codified as `pytest` tests.
- No linting/type-checking configuration (`ruff`/`mypy`) has been set up in this repository yet, unlike the main monolith.
- Chunking is fixed-size (character count) rather than semantic (sentence/paragraph-aware).
- Re-ingesting a lesson currently deletes and recreates its chunks rather than diffing — correct, but not optimized for very large lessons.
